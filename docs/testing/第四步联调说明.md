## 合并及改动范围

当前分支 BranchA，合入的是 moren/BranchB 的 8ff39d2（包含业务实现 7e3f8f7）。合并没有文件冲突，暂不创建合并提交或推送，供用户测试后提交。不要再次发起同一次合并。

所有代码按 README 分包：server 管 HTTP 与业务适配，data 仍由 AppDbHelper 统一建表且 B 的 DAO 执行业务 SQL，api 封装网络与业务调用，ui/BusinessDebugActivity 和 res/layout/activity_business_debug.xml 仅供临时联调。页面文字、选项在 strings.xml 中。

## 关键行为

- 三个 A 的 JSON 接口和十二个 B 的无图接口接入同一 HTTP 主机。图片读取留到第五步。
- public GET /api/posts 和 GET /api/posts/{id} 不要求身份，其余业务接口从 Bearer token 得到真实 memberId。
- 不能通过请求体里的 userId、memberId、ownerId、applicantId 指定操作者；这些字段被拒绝。
- B 的查询改走 BusinessPort.read，完整查询与权限检查在公共锁内完成，不把 SQLiteDatabase 或 Cursor 交给锁外。
- B 的写事务复用 AppDbHelper.withWriteTransaction。抛异常时回滚，并保留 BusinessException 的原始 HTTP 错误码。
- HTTP JSON 请求体仍最多 1 MB，不支持分块请求。当前每次响应后关闭连接，后续请求重新连接。
- 图片工具尚未接入；带图发布返回明确的 400，临时页面只提供无图发布。
- 没有更改数据库版本或表结构，不清除已有身份数据。

## 临时页面使用

主机甲与客户端乙、丙都覆盖安装最新 CampusLostFound.apk。甲保持主机页在前台；乙、丙可以是两台手机，或手机与 MuMu 客户端，或两个分别保存身份的客户端实例。

乙、丙各自连接甲并创建或恢复身份，然后点击“进入业务联调”。进入时会再次验证身份；如果进程重启或验证失效，按提示返回连接页重新检测。

页面上选择操作、填写对应字段，然后点击“发送请求”。返回结果显示 HTTP 状态与 JSON，方便复制其中的帖子 id 和申请 id。这里的 ID 都来自主机返回，不能当作操作者身份。切换操作时 ID 输入框保留，注意当前要求的是“帖子 ID”还是“申请 ID”。

操作列表对应 LostFoundApi 的十二个方法，没有新增调试 HTTP 接口。类型和分类筛选的“全部”只用于查询，发布时必须选择具体值。状态筛选选项随查询对象变化。

## 第一轮：发布、列表、详情与我的发布

1. 乙选择“发布无图帖子”。已有一组测试文字；类型选 FOUND、分类选钥匙，点击发送。
2. 预期 HTTP 200、success=true、status=OPEN，记录 data.id，作为帖子 P。
3. 丙选择“浏览／搜索帖子”，选全部类型、全部分类、全部公开状态，刷新后应看到 P。
4. 丙选择“查看帖子详情”，填 P，应得到同样的公开内容，不出现 proof、contact 或 token。
5. 丙尝试按类型、分类、标题关键词筛选。关键词不匹配时列表为空；普通列表只包含 OPEN 和 RESOLVED。
6. 乙查看“我的发布”应有 P；丙查看自己的发布应没有乙的 P。
7. 乙另发一条 LOST，验证两种类型均可用。每次点击发布会生成新记录，完成后再发下一条。

## 第二轮：申请与权限

1. 丙选择“提交认领／拾获线索”，帖子 ID 填 P，使用页面测试证明与联系方式或自行填写；证明至少 10 字符。
2. 预期 HTTP 200、申请 PENDING，记录申请 data.id，作为申请 C。
3. 丙查看“我的申请”，应看到 C，包含自己提交的证明及联系方式。
4. 乙选择“查看帖子收到的申请”，填 P，应看到 C；丙用同一操作查 P 应返回 403。
5. 丙重复申请 P 应返回 409；乙申请自己的 P 应返回 403。失败不能新增申请记录。
6. 对 LOST 提交的内容按“拾获线索”理解，其他权限及状态规则相同。

## 第三轮：确认、拒绝、取消、关闭及站外完成

这些操作会结束记录或消耗该用户对同帖唯一的一次申请。每组使用新的测试帖子及申请。

- 乙对申请 C 选择“确认完成交接”：申请变 ACCEPTED、帖子变 RESOLVED。丙再次查看自己的申请及帖子，应看到新状态。确认同一条 C 可重复返回当前结果；有第三位申请人时，同帖其他 PENDING 应变 REJECTED。
- 新建帖子及申请后，乙“拒绝申请”，填写原因，应变 REJECTED。申请人不能重新对同帖申请。
- 新建帖子及申请后，丙“取消我的申请”，应变 CANCELLED。乙不能代替申请人取消。
- 新建帖子及申请后，乙“关闭帖子”，应为 CLOSED，所有 PENDING 变 REJECTED；普通列表不再显示，乙的“我的发布”可看到，按 ID 查看详情仍可见。不能继续申请。
- 新建帖子及申请后，乙“标记站外找回／归还”，帖子变 RESOLVED，所有 PENDING 变 REJECTED，不产生 ACCEPTED。
- 非发布者不能确认、拒绝、关闭或标记站外完成；不存在资源返回 404，非法状态操作返回 409。

如有更多客户端，尝试同时确认同帖的两条不同申请，最多一条 ACCEPTED；同时申请与关闭后，CLOSED 帖最终不能留下 PENDING。B 已有 BusinessFlowTest 的并发用例，但它使用独立内存数据，不能代替本次真实 HTTP 与 A 公共数据库的联调。

## 第四轮：断网与持久化

- 甲停止监听后，乙请求应得到连接错误或超时；甲重新开启后可继续操作，身份、帖子、申请仍保留。
- 甲关闭并重新打开 App、手动开启主机，客户端重新检测后，历史记录和原身份仍有效。
- 乙退出临时页面或切到后台会关闭该页面的网络客户端，不回写过期结果；已到达主机的写请求可能仍已完成，重新查询确认，不自动重试 POST。
- 第三步的身份创建和恢复应继续正常。
