# 第三步：数据库与昵称身份

## 范围与目录

本步保持共同接口的 URL、字段、协议版本不变。帖子和申请只建表，不实现 B 的业务 Handler、DAO 或 LostFoundApi。

| 位置 | 职责 |
| --- | --- |
| data/AppDbHelper.java | 主机单例数据库、建表、外键、公共读操作与写事务 |
| data/Member.java | 用户 ID 和昵称，不包含 token 摘要 |
| common/DatabaseLock.java | 全工程唯一 DB_LOCK |
| common/ApiException.java | 统一接口业务异常 |
| server/SessionStore.java | 创建身份、token 摘要入库、查询当前用户 |

| server/LanServer.java | ping、创建身份、恢复身份的 HTTP 路由 |
| server/ServerManager.java | 开启主机时初始化数据库并注入身份工具 |
| api/ClientConnectionStore.java | 私有配置保存 token、用户及主机信息；切换时清理 |

## 接口与身份

- POST /api/sessions：只接受 nickname，去首尾空白后为 1～20 个 Unicode 字符；每次成功创建不同用户，同名不合并。禁止通过 userId、memberId 等指定身份。
- 成功 HTTP 200，data 为 {member:{id,nickname},token,hostId}。
- GET /api/session：携带 Authorization: Bearer token，成功 data 为 {member:{id,nickname},hostId}，不生成或返回新 token。
- token 缺失、格式错误、未知 token 均返回 HTTP 401 及约定的错误包装。
- token 使用 SecureRandom 生成 32 字节，经 Base64 URL-safe 编码成 43 字符；members 仅存 SHA-256 的 64 位十六进制摘要。
- 创建身份的 token 只在首次响应中返回；界面只显示用户 ID、昵称，不显示 token。
- 连接成功后，有旧身份就请求恢复；401 清除失效身份并显示昵称输入；断网和超时保留凭据，不自动创建新用户。
- 更换基础地址先清除旧身份；同地址检测到不同 hostId 也会清除。
- 请求固定 Content-Length，UTF-8 JSON。主机读取时最多 1 MB，超限返回 413；未完整读取、非法 JSON 和未知字段返回 400。不支持分块请求体。
- 当前服务每次响应后关闭该 HTTP 连接。客户端下一次请求会重新连接，避免残留请求体影响后续解析。
- 备份规则排除 client_connection.xml、host_config.xml、数据库及未来 images 私有目录，符合不实现跨设备身份恢复和主机迁移的范围。正常覆盖安装保留数据。

## 数据库结构

数据库名 campus_lost_found.db，版本 1。只创建 members、posts、claims 三张业务表，字段与共同接口约定一致，外键开启且无级联删除。

members.token_hash 唯一且非空，nickname 不唯一；claims 具有 UNIQUE(post_id,applicant_id)。帖子及申请状态和分类通过 CHECK 约束限定。索引：

- posts(owner_id)
- posts(status,created_at,id)
- claims(post_id,status)
- claims(applicant_id,created_at,id)

SQLite 的 AUTOINCREMENT 会由系统维护 sqlite_sequence，它不是额外的业务表。以后升级需编写迁移；不通过删除旧表来升级。

## 给 B 的 Java 接入方式

所有方法在 HTTP 请求线程或 ExecutorService 中调用，不能放主线程。公共入口会检查线程，并使用 common/DatabaseLock.DB_LOCK。不要另建数据库实例或数据库锁。

```java
AppDbHelper helper = AppDbHelper.getInstance(context);

// 只需持有一个工具，读取用户身份也走公共数据库锁。
SessionStore sessions = new SessionStore(helper);
Member member = sessions.requireMemberFromHeader(
        session.getHeaders().get("authorization"));
// 如果已取出原 token，也可 sessions.requireMember(token)。
// member.id 是可信的操作者 ID，不从请求 JSON 读取 ownerId 或 applicantId。

// 只读查询在锁内完成并关闭 Cursor，返回普通值或数据对象。
long count = helper.read(database -> {
    try (Cursor cursor = database.rawQuery("SELECT COUNT(*) FROM posts", null)) {
        cursor.moveToFirst();
        return cursor.getLong(0);
    }
});

// 所有写库都走同一个事务入口，多步业务须在这里重读和检查状态。
helper.withWriteTransaction(database -> {
    // 状态校验和全部数据库更新写在同一个 lambda 中。
    // 业务失败时 throw new ApiException(Response.Status.CONFLICT, "状态已改变");
    return null;
});
```

抛异常会回滚，全部成功才提交。不要把 Cursor 或数据库引用带到锁外处理；图片处理放锁外。AppDbHelper 只维护一个实例，不在每个请求结束时 close。

Handler 可返回 JsonResponse.success(data)，或抛出 ApiException(status,message)。LanServer 的最外层负责统一错误包装，未预期异常只返回“主机内部错误”。

客户端继续通过 LanApiClient.request 调用业务接口；自动附带保存的 token。创建／恢复身份还可用 createSession(nickname,callback)、restoreSession(callback)。这些方法在保存身份成功之后才回调；有新身份或新主机时，旧请求结果不会覆盖当前配置。不要自动重试创建身份 POST，以免重复用户。

## 用户手机测试步骤

先把本次主程序覆盖安装到主机甲和客户端乙；可用另一台手机或 MuMu 作为客户端。两端都需更新，旧主机没有身份接口。不要安装 androidTest 测试包。

1. 甲进入主机页面并开启；乙连接甲。
2. 首次连接应显示昵称输入框。填写昵称后点“使用昵称进入”，应显示身份创建成功、用户 ID 和昵称。
3. 点击“验证当前身份”，应显示身份恢复成功，用户 ID 不变。
4. 乙退出并重新打开 App，再连接同一地址，应自动恢复同一用户，不再次要求昵称。
5. 甲停止并重新开启服务，乙再次连接后身份仍有效。甲关闭并重新打开 App、手动开启主机后也应如此。
6. 甲停止服务时，乙验证身份应提示失败。甲恢复后，乙可继续恢复原身份，不应多出新用户。
7. 乙输入空昵称或超过 20 字的昵称应被拒绝；首尾空白被去除。
8. 若有客户端丙，用同一昵称创建身份，应得到不同 ID。
9. 换另一个主机地址连接，应要求填写新的昵称，不沿用甲的身份；同地址换成不同 hostId 的测试主机也应如此。
10. 在另一设备的浏览器直接访问 http://实际主机IP:8080/api/session（不带 token），应看到 success=false 的身份无效 JSON；客户端正常验证仍成功。
11. 验证途中退出页面或修改地址后重新连接，旧响应不能覆盖新的主机／用户显示。

ID、昵称恢复可通过上述 UI 验收；数据库外键、唯一约束、事务回滚和并发业务需在 B 接入时继续验证。本次不会启动模拟器或运行设备测试，不把编译通过当作手机验收通过。
