## 图片规则和实现

- 系统选择器一次选择一张图片，使用 GetContent 的临时 URI 访问，不新增广泛相册读取权限。
- 先读图片尺寸并采样，再缩到最长边最多 800 像素；按 EXIF 处理旋转和镜像。透明来源转换成白底 JPEG。
- JPEG 从质量 85 逐步压缩；必要时继续降低尺寸，目标不超过 300 × 1024 字节。压缩、解码及网络均不在界面主线程。
- 输出为标准、不换行、带所需填充的 Base64，不带 data: 前缀。客户端源格式是否可读取决于设备解码器，常用 JPEG、PNG、WebP 可先测。
- 主机独立限制 Base64 长度、字符和解码后 500 × 1024 字节；检查 JPEG 标记、MIME 和实际可解码性。非法图片返回 400，超过上限返回 413。
- 请求体总上限仍为 1 MB，沿用 JsonRequest 的有界读取。
- 主机文件位于 App files/images/，以随机 32 位小写十六进制名称加 .jpg 保存；先写临时文件并同步，再重命名为最终文件。保存与解码位于数据库锁外。
- SQLite posts 表只存 image_name。业务写库失败会清理刚保存的图片；清理异常不覆盖原业务异常。
- 图片读取只接受上述随机文件名，并检查规范路径和 posts 引用，不开放目录列表、临时文件或任意路径读取。
- 图片读取无需身份，符合公开帖子图片约定；不存在或非法文件名返回 404 JSON。
- 客户端按当前基础地址加 imagePath 请求图片；不附带 token，拒绝重定向、错误 MIME 和超大响应，后台生成最长边 800 的预览。
- 页面退出后旧网络回调被取消，未显示的 Bitmap 会回收；已显示预览移除引用后交给系统回收，避免渲染线程仍使用时强制 recycle。

## 第五步设备验收流程（保留供回归）

主机甲与客户端乙、丙都覆盖安装最新 CampusLostFound.apk，不需要卸载。也可用手机加 MuMu 客户端；每个客户端需要独立身份。主机持续停在主机页面前台。

1. 甲开启主机，乙连接并恢复身份，进入“业务联调”。
2. 选择“发布帖子（可选图片）”，填写合法字段，点击“选择一张图片”。
3. 从相册或文件选择器选一张物品照片。回到页面后等待身份检查和压缩结束，应显示图片预览、像素及 KB；最长边最多 800，大小最多 300 KB。
4. 点击“发送请求”。预期 HTTP 200，返回 imagePath 为 /images/随机文件名.jpg，页面下方“主机照片已加载”并出现照片。记录帖子 id。
5. 丙连接同一主机并进入业务联调，选择“查看帖子详情”，填该帖子 id 并发送。应显示从甲加载的同一照片。
6. 可以在另一设备浏览器访问“甲的实际地址 + 返回的 imagePath”，直接显示图片，无需 token。不要使用文档中的虚构文件名。
7. 停止甲后再次查询应连接失败；甲重新开启后，查看详情和图片应恢复。甲关闭 App、重新打开并手动开启主机后，原图仍应可读。
8. 乙选择“移除所选图片”，再发布新帖，应返回 imagePath=null，详情显示“这条帖子没有照片”。
9. 原来的发布、查询、申请、状态操作应继续正常。

系统相册打开时页面会暂时进入后台；返回后会重新验证身份并继续处理选图。取消选择保留之前的选图。选图仅在本次页面实例内保存；旋转屏幕或页面被销毁后，重新选择图片。列表仍用于查找 ID，实际照片在发布成功后或“查看帖子详情”时显示。

本次没有拍照入口、多图或单独上传接口；单张图片直接沿用现有发布接口。

## 补充检查

- 选一张竖拍照片，检查方向；再试横拍和透明 PNG。
- 选较大照片，页面应保持可操作的生命周期；压缩过程中发送和选图按钮暂时禁用，避免重复发布。
- 在图片加载时退出，再次进入查询，不应显示上一主机的旧结果。
- 切换网络后使用当前主机地址重新连接，再按原帖子 id 查看，imagePath 不包含旧 IP。
- 访问不存在的合法随机文件名，应返回 404；尝试上级目录或额外路径也不能读到文件。
- 使用请求工具直接提交非 JPEG 的 Base64，期待 400；提交有效但大于 500 KB 的 JPEG，期待 413；请求体超过 1 MB，期待 413。普通选图流程会先压缩，因此不能用它代替这些服务端上限测试。
- 写库失败清理需要在开发测试中模拟事务异常，再检查本次文件是否清理；本轮只核查了这段代码，未运行故障注入。
- 图片文件持久化、设备方向兼容、返回相册的生命周期以及错误图片处理均需用户实际验收。

## 提供给 B 和前端的调用方式

```java
// 在 ExecutorService 中执行；结果包含 jpeg、base64、width、height。
ImageCompressor.CompressedImage image = ImageCompressor.compress(context, selectedUri);
postJson.put("imageBase64", image.base64);
lostFoundApi.publishPost(postJson, callback);

// 使用已有 LanApiClient：图片后台解码，ImageCallback 在主线程收到 Bitmap 或 ApiError。
LanApiClient.RequestHandle handle = client.loadImage(imagePath, imageCallback);
```

图片回调类型是 LanApiClient.ImageCallback，实现 onSuccess(Bitmap) 和 onFailure(ApiError)。取消请求沿用 RequestHandle.cancel；页面结束时 client.close。Bitmap 显示后，替换或销毁时清除 ImageView 和持有引用；未交给 View 的 Bitmap 可以 recycle。

ImageStore.saveJpeg(base64) 返回文件名；imagePath(fileName) 转相对路径；deleteJpeg(fileName) 清理保存失败的本次文件。B 的发布逻辑已经接入，无需再建第二套图片保存工具。普通 JPEG 查询响应不返回 Base64。
