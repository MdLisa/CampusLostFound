## 一 你与另外两位的关系

A 让手机能接收请求、保存数据、识别用户；你决定每个请求具体做什么，并实现业务接口。前端人员下周再根据已完成的接口写界面。三个人开发一个工程，安装同一个 APK。

| 人员 | 负责什么 |
| --- | --- |
| A | 主机启动与停止、局域网连接、数据库基础、身份、图片工具、公共网络请求 |
| 你 | 物品发布与查询、我的发布、申请与处理、完成与关闭、业务数据访问方法 |
| 前端人员 | 正式界面和交互，详细计划下周再写 |

你维护 PostHandler、ClaimHandler、PostDao、ClaimDao、LostFoundApi。A 维护 HTTP 入口和公共工具。HTTP 路由由 A 分发到你的 Handler，不需要 Controller、Spring 注解或 MyBatis。

## 二 第一版必须完成的功能

1. 发布寻物或招领：标题、描述、分类、地点，可选一张图片。
2. 浏览和搜索：按类型、分类、标题关键词查找。
3. 查看详情和我的发布。
4. 对招领提交认领证明；对寻物提交拾获线索，均附联系方式。
5. 查看我提交的申请和我收到的申请。
6. 发布者线下核实、交接后确认完成；也能拒绝申请。
7. 申请人能取消待处理申请；发布者能关闭帖子，或标记站外找回。

不做管理员、评论、收藏、聊天、举报、密码登录、推送和多轮审核。第一版不做帖子修改和删除，填写错误时关闭后重新发布，减少接口和状态复杂度。

## 三 业务规则

帖子分 LOST 寻物和 FOUND 招领，共用一套接口。分类固定为 CARD、ELECTRONICS、KEYS、BOOKS、DAILY、OTHER，名称由共同接口约定给出。

帖子只有 OPEN、RESOLVED、CLOSED 三种状态。申请只有 PENDING、ACCEPTED、REJECTED、CANCELLED 四种状态。

FOUND 的申请填写物品特征证明；LOST 的申请填写拾获线索。proof 和 contact 只对申请人和发布者可见，不出现在公开帖子接口。

“确认完成”表示线下已经交接，不只是审核通过。确认后帖子 RESOLVED，对应申请 ACCEPTED，其他 PENDING 自动 REJECTED。不设置交接中的中间状态。

同一用户对同一帖子最多一条申请，取消或拒绝后不能重投。不能申请自己的帖子。非 OPEN 帖不能产生新申请。身份只从 A 的 token 校验结果获得，不接收客户端 userId 指定操作者。

## 四 你负责的十二个 HTTP 接口

所有路径加 /api 前缀。字段、返回和校验以共同接口约定为准。

| 方法 | 地址 | 功能 |
| --- | --- | --- |
| POST | /posts | 发布物品信息 |
| GET | /posts | 列表、搜索和分类筛选 |
| GET | /posts/{postId} | 查看物品详情 |
| GET | /me/posts | 查看本人发布 |
| POST | /posts/{postId}/claims | 提交认领或拾获线索 |
| GET | /me/claims | 查看本人提交的申请 |
| GET | /posts/{postId}/claims | 查看某帖子收到的申请，仅发布者 |
| POST | /claims/{claimId}/confirm | 发布者确认已完成交接 |
| POST | /claims/{claimId}/reject | 发布者拒绝申请 |
| POST | /claims/{claimId}/cancel | 申请人取消申请 |
| POST | /posts/{postId}/resolve | 发布者标记站外找回或归还 |
| POST | /posts/{postId}/close | 发布者关闭信息 |

公开列表与详情不用身份，其余均带 token。列表先限制最多返回最新 100 条，配合筛选足够用于课设；不实现复杂分页和无限滚动，返回中说明是否截断。

## 五 数据库和数据访问

A 统一维护 AppDbHelper 和建表语句，你与 A 确认 posts、claims 字段，然后编写这两张表的操作方法。

PostDao 至少提供：新增帖子、按筛选查询、按 ID 查询、查询本人帖子、更新帖子状态。

ClaimDao 至少提供：新增申请、检查重复、查询本人申请、查询收到的申请、按 ID 查询、更新目标申请状态、拒绝某帖的其他待处理申请。

SQL 使用占位参数，不拼接用户输入。公开查询不带 contact 或 proof；申请查询先验证权限，再执行或返回私有字段。Cursor 使用完及时关闭。

对外 JSON 字段名固定用 camelCase，数据库列名可以用下划线。方法返回对象或 JSON 均可，但前后保持一致，不各自起不同字段名。

## 六 最重要的事务

所有写操作使用 A 提供的公共锁和 SQLite 事务，不使用 MySQL 的 SELECT FOR UPDATE。

确认申请的顺序：

1. 在公共锁与事务中重新查询申请和帖子，验证登录者是发布者。
2. 检查帖子为 OPEN、申请为 PENDING。
3. 将目标申请更新为 ACCEPTED。
4. 将帖子更新为 RESOLVED。
5. 将同一帖其他 PENDING 申请更新为 REJECTED，并填写固定原因。
6. 全部成功后提交，任何失败回滚。

发布者重复确认同一条已经 ACCEPTED 的申请，可以返回当前结果；确认其他已被拒绝的申请返回 409。两个请求同时确认不同申请，最多一个成功。

关闭和站外完成也在同一事务中结束所有 PENDING。取消、拒绝、提交申请同样使用公共锁，避免在帖子关闭后留下待处理申请。

## 七 给前端留一层容易调用的方法

在 api 包的 LostFoundApi 中封装业务方法，内部调用 A 的 LanApiClient。这样前端只关心字段和结果，不必自己重复拼 URL。

建议方法：publishPost、listPosts、getPost、getMyPosts、submitClaim、getMyClaims、getReceivedClaims、confirmClaim、rejectClaim、cancelClaim、resolvePost、closePost。

方法名只是 Java 调用约定，不是十二套额外接口。参数和回调按共同接口约定组织。先用 JSONObject 即可，不要求泛型网络框架、依赖注入或复杂 Repository 分层。

前端没开始时，使用临时调试按钮或请求工具验证；不需要你提前完成正式界面。临时界面只用于确认功能能调用。

## 八 开发顺序

| 顺序 | 任务 | 验证方式 |
| --- | --- | --- |
| 第 1 步 | 和 A 确认字段、状态、身份及公共锁 | 按共同接口约定写出请求示例 |
| 第 2 步 | 无图发布、列表、详情、我的发布 | 手机甲发布，手机乙刷新能看到 |
| 第 3 步 | 提交、我的申请、收到的申请 | 手机乙申请，手机甲查看联系方式 |
| 第 4 步 | 确认、拒绝、取消、关闭、站外完成 | 业务状态能完整变化 |
| 第 5 步 | 接入 A 的单图保存工具 | 发布带图信息，另一台手机能显示 |
| 第 6 步 | 完成 LostFoundApi 和跨手机测试 | 前端可直接接方法做界面 |

第一周优先完成无图发布、查询、提交申请；第二周完成状态处理、图片和接口确认；后面配合前端和答辩。下周根据实际进度编写前端计划，不必等所有边角问题处理完。

## 九 验收标准

- [ ] 两台客户端连到同一主机，能看到同一批帖子。
- [ ] 两种类型都能发布，分类和标题搜索有效。
- [ ] 公开接口不泄露联系方式、token 或证明。
- [ ] 不能以修改请求里的 userId 冒充别人。
- [ ] 自己不能申请自己发布的帖子，同一帖子不能重复申请。
- [ ] 只有发布者能读取收到的申请、确认或拒绝。
- [ ] 只有申请人能取消自己的待处理申请。
- [ ] 确认一条后，帖子完成，其他待处理申请自动拒绝。
- [ ] 关闭和站外完成后不能继续申请。
- [ ] 同时确认两条申请时最多一条通过。
- [ ] 主机重新启动后，发布和申请记录还在。
- [ ] 列表为空、断网和状态不允许时都有明确结果。

演示至少准备一条 LOST 和一条 FOUND 帖子，分别走通流程。不要为了展示数据而另外增加统计系统。
