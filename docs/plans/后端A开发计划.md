# 校园失物招领 App 手机主机与数据开发计划

负责人：开发人员 A。版本：0.2，2026 年 10 月 22 日。

实施进度（2026 年 10 月 26 日）：第 1～5 步已完成实现，用户反馈各阶段测试通过；第 5 步提交为 8ea082e。第 6 步正在收尾，已补充异常恢复处理与回归测试源码，实际设备验收仍待完成。构建结果和逐项测试方法见 docs/testing/第六步测试与交接说明.md；下方验收框保留给完整验收时逐项确认。

你负责把一台安卓手机变成局域网内的主机，让其他手机能连接它，并把大家的数据保存在这台手机里。全部代码都在同一个 Android Studio 工程中开发。本计划替代之前的独立服务器方案。

## 一 最终做出来是什么样

所有手机安装同一个 APK。启动后选择“开启主机”或“连接主机”。演示时一台手机专门停在主机页面，另外两台手机作为普通用户操作。

主机页面显示服务是否开启、主机局域网 IP 和端口，例如 http://192.168.1.20:8080。客户端手动输入地址，连接成功后填写昵称进入系统。IP 只是示例，每次以现场实际地址为准。

所有帖子、用户身份和申请记录都保存在主机的 SQLite 数据库中，照片放在主机 App 私有目录。客户端不各自保存一套业务数据库，只通过网络读写主机数据。先不实现离线使用或自动同步。

## 二 统一技术选择

| 工作 | 选用方式 |
| --- | --- |
| 开发工具 | 全员 Android Studio，共用一个安卓工程 |
| 语言和界面 | Java 和 XML |
| 手机内的 HTTP 服务 | NanoHTTPD，只引入核心库 |
| 本地数据库 | SQLiteOpenHelper 和 SQLite |
| 客户端网络请求 | HttpURLConnection，封装一次让队友复用 |
| JSON | Android 自带 JSONObject 和 JSONArray |
| 并行工作 | ExecutorService，网络和数据库不放在界面主线程 |
| 图片 | 第一版每帖最多一张 JPEG，压缩后再传 |

不再单独搭建网站服务，不安装外部数据库，也不使用复杂的分层框架。Android Studio 和 Gradle 的构建环境按工程模板配置，三个人使用同一份项目配置。

SQLiteOpenHelper 是安卓提供的底层数据库工具；这个课设只有三张表，选它是为了减少额外库。主机使用 NanoHTTPD 接收 HTTP 请求，客户端通过请求地址获取 JSON，不需要自己设计原始 Socket 协议。

## 三 你的具体工作

### 1 创建工程和公共结构

建立同一个 app 模块，建议按 ui、server、data、api、common 分包即可。提交可运行工程后，B 直接在其中加入业务逻辑。

你维护：LanServer、ServerManager、AppDbHelper、SessionStore、ImageStore、LanApiClient 和临时 HostActivity。B 维护：PostHandler、ClaimHandler、PostDao、ClaimDao、LostFoundApi。类名可以调整，但不要互相另建第二套网络或数据库工具。

### 2 主机的开启和关闭

主机页有开启、停止、地址展示、运行状态四项。端口固定 8080，重复点击不能启动多个监听器；端口被占用时要显示失败原因。监听局域网可连接的网卡地址，不只监听 127.0.0.1。

第一版只要求主机页面在前台、屏幕保持亮起。主机进入后台或退出页面时停止监听，回到页面后手动重新开启。不要设计锁屏常驻、开机启动或复杂保活。

主机对象由 ServerManager 统一管理。界面重新创建、连续点击启动、页面退出都必须正确停止或复用实例，避免端口占用。停止监听不清空数据库和照片。

### 3 连接检测和客户端请求工具

实现 GET /api/ping，返回应用标识和协议版本。客户端必须检查响应中的 app 和 protocolVersion，不能只要 HTTP 200 就认为连对了主机。

LanApiClient 统一处理基础地址、GET 和 POST、JSON、token 请求头、超时和失败回调。设置连接与读取超时，例如各 5 秒。后台执行请求，回到主线程后再通知界面显示结果。

客户端手动填写 http://主机IP:8080，不做自动发现、扫码或广播搜索。保存最近连接地址；更换地址时必须清除原身份，防止把旧主机的身份用于新主机。

### 4 简化身份

不做账号密码注册。用户第一次连接后填昵称，主机生成 memberId 和随机 token。昵称允许重复，身份以 token 为准。

主机在 members 表保存 token 的 SHA-256 摘要，客户端在 App 私有 SharedPreferences 中保存原 token 和主机标识。每次写业务请求和查询个人记录时携带 token，服务端查出当前 memberId，不能信任请求体里的 userId。

POST /api/sessions 创建身份。旧客户端连接同一主机后，可用 GET /api/session 检查原身份是否有效；有效就继续使用，不要每次启动都生成新用户。无效时提示重新输入昵称。

不设置密码找回、身份合并或跨手机登录。客户端卸载或清空数据会丢失本机身份；主机卸载或清空数据会丢失所有业务数据。演示账号和帖子用测试资料。

### 5 SQLite 数据库

只建三张表：members、posts、claims。你负责统一 AppDbHelper、建表和数据库版本；B 负责帖和申请的查询、更新方法。具体字段见共同接口约定。

全工程共用一个 AppDbHelper。所有数据库写操作统一通过一个 Java 公共锁串行进入；涉及多条更新时同时用 SQLite 事务。B 不再创建自己的数据库实例或另一套锁。

主机重启后，帖子、申请和用户身份仍应存在。hostId 是主机初始化时生成并持久化的标识，App 普通重启不能改变，清空主机数据才重新生成。

### 6 单张图片工具

先做通无图业务，再补图片。客户端把图片压缩为 JPEG，最长边不超过 800 像素，目标不超过 300 KB，再转 Base64 放在发布 JSON 里。服务端再次检查，拒绝实际超过 500 KB 或无法解码的图片；请求体总大小最多 1 MB，限制在读入全过程生效。

你提供客户端压缩方法和主机 ImageStore 保存方法。文件名由主机随机生成，只允许从指定图片目录读取，禁止把任意路径当文件名使用。

B 发布帖子时调用 ImageStore，posts 表只存 image_name。接口返回相对地址 imagePath，例如 /images/abc123.jpg。客户端用当前主机基础地址拼接，避免换 Wi-Fi 后数据库中的旧 IP 导致图片失效。

GET /images/{fileName} 返回 JPEG 二进制，不返回 JSON。照片只作为公开帖子图片，不上传完整证件或私人证明。第一版没有单独上传接口和文件记录表。

## 四 你负责的四个 HTTP 接口

下表三个 JSON 接口使用 /api 前缀，图片接口不加。完整字段在共同接口约定中。

| 方法 | 地址 | 功能 |
| --- | --- | --- |
| GET | /api/ping | 检查主机、协议版本和 hostId |
| POST | /api/sessions | 昵称进入，生成用户身份和 token |
| GET | /api/session | 验证已有 token，恢复本机身份 |
| GET | /images/{fileName} | 从主机获取已发布图片 |

你还提供 Java 内部方法，供 B 调用：

| 方法语义 | 用途 |
| --- | --- |
| requireMember(token) | 校验 token，返回当前用户 ID 和昵称 |
| jsonSuccess(data) 和 jsonError(status, message) | 统一返回结构 |
| saveJpeg(base64) | 验证并保存图片，返回随机文件名 |
| imagePath(fileName) | 把文件名转换成相对访问路径 |
| withWriteTransaction(work) | 在公共锁内开启事务，成功提交、失败回滚 |
| LanApiClient.request(method, path, body, callback) | 队友不用重复写网络请求、超时和线程切换 |

以上是方法职责示意，不要求实现复杂泛型框架。

## 五 Android 和局域网的必要配置

- 声明 INTERNET 和 ACCESS_NETWORK_STATE 权限；演示版明确允许局域网 HTTP，避免客户端被明文通信策略拦截。
- 如果目标 SDK 为 37 或以上，按 Android 官方要求声明并申请局域网访问权限，主机和客户端都要处理；目标 SDK 不超过 36 时按对应版本规则配置。你统一处理，B 不重复研究。
- 主机显示正确的 Wi-Fi 或热点网段 IPv4；有多个地址时允许手工确认，不把移动网络或 VPN 地址直接作为连接地址。
- 优先使用可互访的 Wi-Fi 路由器。也可以用一台手机开热点，再测试其余手机能否访问主机；不要硬编码热点网关 IP。
- 校园 Wi-Fi 可能禁止设备互访，第一天就要用两台真机测试。不要等业务做完才发现网络环境不通。

主机只保持前台是本课设的范围约束，不承诺切到后台、锁屏或进程被系统结束后还能继续服务。

## 六 开发顺序

| 顺序 | 你的目标 | 可以看到的结果 |
| --- | --- | --- |
| 第 1 步 | 两台真机连接同一网络，做出主机和 ping | 另一台手机的浏览器能看到正确的 JSON |
| 第 2 步 | 加入主机开关、HTTP 配置、LanApiClient | 客户端临时按钮能检测并连接主机 |
| 第 3 步 | 三张表、身份创建和恢复、公共事务工具 | B 能取得当前用户并调用数据库 |
| 第 4 步 | 把公共工程交给 B，同步测试其接口 | 一台主机能接收多个手机的请求 |
| 第 5 步 | 单图压缩、保存、读取 | 手机甲发布的照片能在手机乙显示 |
| 第 6 步 | 网络断开、重复启动、主机重启等测试 | 失败有提示，重启后原数据仍在 |

时间参考：第一周完成前 3 步并交给 B；第二周补图片、配合联调；后面配合前端和答辩。实际以课程截止时间为准。下周制定前端计划前，至少交出能连接的真机地址和身份接口。

## 七 完成验收

- [ ] 只用 Android Studio 就能构建 APK，不需要外部服务器和数据库服务。
- [ ] 两台真机的 ping 连通，能核对 app、protocolVersion 和 hostId。
- [ ] 主机能启动、停止，重复点击不会重复监听；退出后状态准确。
- [ ] 未知 token 不能伪造用户；更换主机不会带错身份。
- [ ] 主机普通重启后 hostId、用户、帖子和申请仍然存在。
- [ ] 所有写库操作使用同一把锁，多步操作支持事务回滚。
- [ ] 超时、断网、权限被拒绝时客户端能收到明确错误，界面不卡住。
- [ ] 单张图片能跨手机显示，超大或非法图片被拒绝。
- [ ] 主机页面前台持续运行时，三台手机能完成一次演示。
