# 校园寻物站 App 前端开发计划

负责人：前端开发人员。日期：2026 年 10 月 28 日。版本：1.0。

你负责把目前用于测试的界面整理成普通用户可以直接使用的 App。A、B 已完成主机、数据、图片和业务功能，已合入 master；用户已反馈最新安装包测试完成。本计划依据 master 的 187765c 和现有 Java 方法编写，后续在同一工程中实现正式界面。

目标是完成现有失物招领流程，不增加新的业务范围。完成本计划并通过验收后，主要剩下问题修复、合并和课设演示，不再额外安排一轮功能开发。

| 人员 | 已有职责 | 前端阶段怎样配合 |

## 二 技术和工作范围

全部继续使用 Android Studio、Java 和 XML，同一个 app 模块、同一个 APK。新页面采用普通 Activity；列表先使用 Android 自带 ListView 和 BaseAdapter，选择项用 Spinner 或 RadioGroup，申请与拒绝原因用对话框即可。

不要求引入 Compose、Kotlin、复杂导航框架、MVVM、依赖注入或新的图片库。现有 Material 组件可以使用，不为样式单独更换技术栈。

必须实现的用户能力：连接主机、昵称进入、浏览搜索、查看详情、发布单图信息、提交认领或拾获线索、查看我的发布与申请、处理收到的申请、确认归还、关闭与站外完成。

不安排账号密码、管理员、聊天、评论、收藏、地图、推送、多图、帖子修改删除、主机后台常驻和自动同步。这些不属于本次前端任务。

## 三 页面与跳转

不必一次创建全部页面，按第八节顺序逐步完成。

| 页面 | 建议文件 | 必须包含的内容 |
| --- | --- | --- |
| 启动入口 | 复用 MainActivity 和 activity_main.xml | 显示“校园寻物站”，提供“开启主机”和“连接主机”两个入口 |
| 主机页 | 复用 HostActivity 和 activity_host.xml | 地址、运行状态、开启、停止、刷新地址，提示保持页面前台 |
| 连接页 | 复用 ConnectActivity 和 activity_connect.xml | 地址检测、昵称进入或恢复身份、明确的连接反馈；身份有效后进入首页 |
| 信息首页 | PostListActivity 和 activity_post_list.xml | 信息列表、搜索、类型与分类筛选、刷新、发布入口、我的记录入口 |
| 物品详情 | PostDetailActivity 和 activity_post_detail.xml | 图片、标题、描述、地点、类型、分类、发布者、时间、状态及对应操作 |
| 发布页 | PublishPostActivity 和 activity_publish_post.xml | 类型、标题、描述、分类、地点、一张图片预览、移除图片、发布 |
| 我的记录 | MyRecordsActivity 和 activity_my_records.xml | “我的发布”和“我的申请”两组选项，列表、状态筛选、刷新和对应操作 |
| 收到的申请 | ReceivedClaimsActivity 和 activity_received_claims.xml | 指定帖子的申请列表、证明或线索、联系方式、状态、确认与拒绝 |

申请表单放在详情页的对话框，拒绝原因也用对话框，不再额外创建两个 Activity。我的记录可用两个按钮或 RadioGroup 切换模式，不要求复杂底部导航。

主要流程：入口 → 连接页 → 首页 → 详情页 → 提交申请。发布入口从首页进入，发布成功后打开该条详情。我的发布点击记录也打开同一个详情；发布者从详情进入收到的申请。

页面跳转只传必要 ID，例如 postId；申请操作从列表记录取得 claimId。正式页面不显示“请求方法”“HTTP 状态”“JSON 输出”等调试控件，也不要求用户填写帖子 ID 或申请 ID。BusinessDebugActivity 可以保留给开发回归，普通用户流程不再依赖它。

## 四 各页面的功能要求

### 1 入口 主机和连接页

先修改文字、排版和按钮，不重写核心逻辑。主机仍是独立角色，演示时专门使用一台手机停在主机页；不要在主机手机跳到客户端首页，导致主机因离开前台而停止。

主机页复用原串行启停队列和权限处理，开启、停止仍在后台执行。离开前台即停止，重新进入手动开启，不增加后台服务。

连接页复用 connect、createSession 和 restoreSession。有有效身份时直接进入首页；无身份才输入昵称。显示“已连接”“连接失败”“正在恢复身份”等普通文字，不展示 token。更换地址会清除原身份，沿用现有提示规则，不增加退出登录或身份找回功能。

连接页可以保留“进入首页”按钮，只有身份成功后启用；不需要反复自动创建昵称身份。

### 2 首页

列表每条先显示标题、寻物或招领、地点、分类和状态即可。照片优先在详情页展示，第一版不要求为一百条记录同时加载缩略图。

支持类型 LOST、FOUND 或全部，分类六项或全部，公开状态 OPEN、RESOLVED 或全部，以及标题关键词。设置一个搜索或刷新按钮即可，不要求边输入边请求，也不要求无限滚动。

“全部”传 null，不传中文“全部”或空字符串。输入框内容去首尾空白，空关键词传 null。列表最多最新 100 条；hasMore 为 true 时提示“仅显示最新 100 条，可缩小筛选范围”，不做分页。

点击记录取得 id，进入详情页。首次加载有等待提示；没有记录显示空列表说明；失败显示原因和重试入口，不把失败当作没有记录。返回首页时重新请求，能看到刚发布或刚完成的信息。

### 3 详情与申请表单

详情用 getPost(postId) 获取，不只依靠首页传来的旧数据。createdAt 是毫秒时间戳，用本机日期格式展示。imagePath 为 null 时显示无图占位；有图时复用 client.loadImage，加载失败不影响文字和按钮。

当前用户 ID 从 restoreSession 成功返回的 member.id 获取；帖子发布者 ID 来自 owner.id。不要通过昵称判断是不是本人，也不要直接读写私有 SharedPreferences 的内部键。

| 当前情况 | 显示哪些操作 |
| --- | --- |
| 他人 FOUND 且 OPEN | “申请认领”，填写物品特征和联系方式 |
| 他人 LOST 且 OPEN | “提供拾获线索”，填写线索和联系方式 |
| 本人 OPEN | “查看收到的申请”“标记已找回或归还”“关闭信息”，不显示申请自己的按钮 |
| RESOLVED | 显示“已完成”，不再允许新申请或关闭 |
| CLOSED | 显示“已关闭”，不再允许新申请；发布者仍可查看历史申请 |

申请表单 proof 为 10～300 字符，contact 为 3～80 字符。提交期间禁用重复点击；成功后提示并提供进入我的申请的路径。服务端返回 409 时展示已申请或状态不允许的原因，不强行再次发送。

站外完成调用 resolvePost，表示已经通过其他途径找回或归还；closePost 表示不再继续受理，两者不能用同一个按钮混淆。操作前提示影响，成功后重新获取详情。

### 4 发布页

字段严格沿用现有接口：type、title、description、category、location，可选 imageBase64。发布者身份由公共工具自动附带，页面不传 ownerId。

校验：标题 2～40 字符，描述 5～500 字符，地点 2～60 字符；类型与分类必须选具体值。描述里可以填写丢失或拾获时间，不另加必填日期接口。

选图、压缩、预览和移除复用现有 ImageCompressor 及调试页实现。最长边不超过 800 像素、客户端目标 300 KB，输出为 JPEG Base64；主机仍负责 500 KB 图片和 1 MB 请求上限。压缩放后台，选图返回后先恢复身份再允许发送。

无图时不传 imageBase64 或传 null。等待压缩和发送时禁用发布按钮。成功后用返回的帖子 ID 打开详情，结束发布页，避免返回时误点再发。

网络错误不自动重发发布请求，提示先看我的发布确认是否已成功。表单在同一页面实例内尽量保留；旋转或重建后至少不自动提交，图片丢失时提示重新选择，不要求实现完整草稿系统。

### 5 我的发布 我的申请和收到的申请

我的发布显示全部本人记录，状态可筛 OPEN、RESOLVED、CLOSED；点击进入同一个详情页。

我的申请显示帖标题、寻物或招领、申请状态和处理说明，可展开显示本人提交的内容，点击标题进入帖子详情。申请为 PENDING 且 postStatus 为 OPEN 时显示“取消申请”，其他状态只展示结果。

收到的申请从本人帖子进入，调用 getReceivedClaims(postId, status)。显示申请人昵称、证明或线索、联系方式、状态和 note。PENDING 且帖子 OPEN 时才提供确认与拒绝；拒绝原因 2～100 字符。

“确认归还完成”必须提示：只有线下交接已经完成才确认，确认后帖子完成，其他待处理申请会自动拒绝。成功后刷新整个收到申请列表及帖子状态，不只改变当前按钮文字。

所有申请页遵守服务端权限，403 时提示无法操作。公开首页和详情不展示其他人的 proof、contact。联系方式显示为文字即可，不要求拨号、微信跳转或聊天。

## 五 直接复用的 Java 方法和接口

本节按实际源代码列出，参数顺序不可自行调换。字段和状态的最终约定参见 [共同接口约定](../api/共同接口约定.md)。

### A 的基础能力

| 调用 | 用在哪里 | 注意事项 |
| --- | --- | --- |
| client.connect(address, callback) | 连接页 | 检查 ping、app、协议和 hostId，不携带旧 token |
| client.createSession(nickname, callback) | 首次昵称进入 | 创建并保存身份，成功后才进入首页 |
| client.restoreSession(callback) | 恢复身份及业务页面重新进入 | 返回 member、hostId，不新建身份 |
| ClientConnectionStore.getInstance(context).getBaseAddress() | 回填地址 | 身份与地址由原工具管理，不手动保存 token |
| ImageCompressor.compress(context, selectedUri) | 发布选图 | 必须后台调用，结果包含 base64、jpeg、width、height |
| client.loadImage(imagePath, imageCallback) | 详情图片 | ImageCallback 成功返回 Bitmap，失败返回 ApiError |
| client.close() | 页面停止时 | 关闭后不能复用，重新进入创建新实例 |

connect 对应 GET /api/ping；createSession 对应 POST /api/sessions；restoreSession 对应 GET /api/session；loadImage 对应 GET /images/{fileName}。主机开关继续复用 HostActivity 和 ServerManager，不是新 HTTP 接口。

### B 的十二个业务方法

下面省略每个方法最后一个相同的 callback 参数，实际调用时必须传入。

| 方法和参数顺序 | HTTP 接口 | 页面用途 |
| --- | --- | --- |
| publishPost(body) | POST /api/posts | 发布 |
| listPosts(type, category, keyword, status) | GET /api/posts | 首页列表和搜索 |
| getPost(postId) | GET /api/posts/{postId} | 详情 |
| getMyPosts(status) | GET /api/me/posts | 我的发布 |
| submitClaim(postId, body) | POST /api/posts/{postId}/claims | 申请或提供线索 |
| getMyClaims(status) | GET /api/me/claims | 我的申请 |
| getReceivedClaims(postId, status) | GET /api/posts/{postId}/claims | 收到的申请 |
| confirmClaim(claimId) | POST /api/claims/{claimId}/confirm | 确认完成交接 |
| rejectClaim(claimId, reason) | POST /api/claims/{claimId}/reject | 拒绝 |
| cancelClaim(claimId) | POST /api/claims/{claimId}/cancel | 取消 |
| resolvePost(postId) | POST /api/posts/{postId}/resolve | 站外找回或归还 |
| closePost(postId) | POST /api/posts/{postId}/close | 关闭信息 |

每个业务页面在 onStart 创建自己的 LanApiClient，再创建 LostFoundApi(new LanApiTransport(client))。先恢复身份，成功后读取业务数据和启用写按钮。若进程重启后尚未检测连接，返回连接页先 connect；hasIdentity 只表示存有凭据，不代表已经完成连接验证。

### 两种回调不要混淆

LanApiClient.Callback 的 onSuccess(JSONObject data) 已经拆掉 success、message、data 外层；例如身份回调直接读取 data.member。

LostFoundApi.Callback 为 onResult(int httpStatus, JSONObject response, Exception error)，成功时 response 仍含完整包装，业务数据在 response.data。

| 业务回调情况 | 判断和处理 |
| --- | --- |
| 成功 | httpStatus 为 200，error 为 null，从 response.data 取对象 |
| HTTP 业务失败 | httpStatus 为 400、401、403、404、409、413 或 500 等，error 为 null，从 response.message 取原因 |
| 本地或网络失败 | httpStatus 为 0，response 为 null，error 非空，显示错误并允许重新查询 |

业务列表的数据在 response.data.items，hasMore 在 response.data.hasMore；不是直接从 response 取 items。JSONObject 的可空字段先检查 isNull，避免把 null 显示成文字“null”。

下面只示意已连接并验证身份后的读取位置，不是一份完整 Activity：

```java
LanApiClient client = new LanApiClient(getApplicationContext());
LostFoundApi api = new LostFoundApi(new LanApiTransport(client));
api.listPosts(null, null, null, null, (httpStatus, response, error) -> {
    if (error != null) {
        // 网络或本地失败，显示 error.getMessage()。
        return;
    }
    if (httpStatus != 200) {
        // 业务失败，显示 response 中的 message。
        return;
    }
    JSONObject data = response.optJSONObject("data");
    // data.optJSONArray("items") 交给列表 Adapter。
    // data.optBoolean("hasMore") 决定是否显示条数提示。
});
```

现有网络回调已在主线程，可更新界面；图片压缩和耗时工作仍在后台。不要为 JSONObject 解析或数据展示另建数据库和服务端业务。

## 六 页面状态和返回行为

每个请求页面至少区分正在加载、成功有数据、成功无数据、失败四种情况。按钮文字和错误提示面向普通用户，不展示 SQL、堆栈、token 或原始请求日志。

| 情况 | 页面应该怎样处理 |
| --- | --- |
| 401 身份失效 | 禁用业务操作，返回连接页重新进入，避免返回键又回到失效业务页 |
| 403 无权操作 | 显示原因并刷新或返回，不靠重新发送绕过 |
| 404 不存在 | 提示信息不存在，提供返回列表 |
| 409 重复或状态冲突 | 显示原因，重新查询申请或帖子状态 |
| 413 图片或请求过大 | 提示重新选图或压缩，不自动重试 |
| 连接失败或超时 | 保留身份，允许重新查询；不自动生成新用户或重发业务 POST |

页面 onStop 调用本页 client.close，取消旧页面回调；onStart 创建新实例、恢复身份并重新读取数据。不要把 Activity、View 或已关闭的 client 放入静态变量，也不要直接在主线程请求网络。

选图会让发布页暂时停止，返回后重新建立客户端并验证身份。待处理 URI、压缩结果和表单保留在合适的页面状态中；只有页面仍有效时更新预览。可以参考 BusinessDebugActivity 的处理，不直接删除它的生命周期保护代码。

列表刷新时避免旧请求覆盖新筛选结果；可在一次刷新未结束时禁用再次搜索，或使用本页请求序号，只接收当前一轮结果。业务写入未返回结果就离开页面时，回到记录页先查实际状态，不认为退出页面已经撤销写入。

写请求发生超时、断网或页面中断，主机可能已经处理成功。统一提示“操作结果尚未确认，请先查看记录”，发布看我的发布，申请看我的申请，处理申请看收到的申请。禁止盲目自动重发 POST。

## 七 文件归属和交付内容

建议只新增五个正式业务 Activity：PostListActivity、PostDetailActivity、PublishPostActivity、MyRecordsActivity、ReceivedClaimsActivity。三个现有入口页面继续复用；类名可以调整，但不要为每种状态各建一套页面。

| 目录或文件 | 本阶段的改动 |
| --- | --- |
| ui | 新增正式页面与列表 Adapter，整理已有入口、主机和连接页 |
| res/layout | 页面 XML、帖子条目 item_post.xml、申请条目 item_claim.xml、申请和原因表单 |
| res/values/strings.xml | 应用显示名“校园寻物站”、用户提示、分类和状态中文文字 |
| res/values/colors.xml 与 themes.xml | 使用同一套颜色和主题，正文清楚、按钮大小合适 |
| res/drawable | 必要的无图占位和简单图标，不要求设计复杂插画 |
| AndroidManifest.xml | 注册新增 Activity，保留现有权限、网络和备份配置 |
| docs | 记录前端完成情况、验证结果和待修问题 |

布局不写死屏幕像素，尺寸用 dp、文字用 sp；表单可滚动，键盘弹出后仍能操作提交按钮。先做到可读和易操作，再统一间距与颜色，不以动画或视觉特效作为验收重点。

交付内容是可构建的代码、最新 APK、页面对应方法清单和一份简短测试记录。测试记录写明已测设备、通过项目、未测项目和已知问题，不要求每一步都生成一份长文档。

## 八 开发顺序

| 顺序 | 任务 | 验证方式 |
| --- | --- | --- |
| 第 1 步 | 整理入口与连接页，新建首页并接上 listPosts | 客户端昵称进入后看到真实帖子列表，临时业务页仍可用于回归 |
| 第 2 步 | 首页筛选、详情、图片和申请表单 | 点击帖子进入详情，无需填 ID；另一用户能提交申请 |
| 第 3 步 | 发布表单、选图压缩和发布成功跳转 | 手机乙发布，手机丙刷新看到文字和详情照片 |
| 第 4 步 | 我的发布、我的申请、收到的申请，以及确认、拒绝、取消、关闭、站外完成 | 用户从正常界面完成整个状态流程 |
| 第 5 步 | 加载、空列表、失败提示、页面返回、选图返回和防重复点击；统一样式 | 断网有提示，返回会刷新，权限和业务错误不导致崩溃 |
| 第 6 步 | 三台真机完整验收、修复问题、整理交付记录 | 全程不进入调试页、不输入资源 ID，也能完成演示 |

时间参考：前半段先完成第 1～3 步，后半段完成第 4～6 步，按课程截止日期调整。每一步做通后再继续，不先画完所有页面才第一次接接口。

从最新 master 建前端分支（例如 dev-ui），小步提交。完成并验收后再合入 master；本计划本身不自动创建分支、提交或推送。

## 九 完成验收清单

- [ ] 一个 APK 内仍能选择主机和客户端；主机正常启停、地址显示正确。
- [ ] 昵称进入和身份恢复可用，不展示 token，也不在每次启动时新建用户。
- [ ] 首页能浏览、搜索和筛选真实数据，空列表与失败区别清楚。
- [ ] 点击记录能进详情，界面不要求输入帖子或申请 ID，不依赖原始 JSON。
- [ ] LOST 和 FOUND 文字及申请提示不同，类型、分类和状态都显示中文含义。
- [ ] 可以无图或单图发布，另一客户端看到同样的文字与详情图片。
- [ ] 只有非发布者且 OPEN 时显示申请入口；服务端仍执行最终权限判断。
- [ ] 我的发布、我的申请、收到的申请数据归属正确，公开页不泄露申请内容和联系方式。
- [ ] 确认完成、拒绝、取消、关闭和站外完成全部能从正常按钮操作。
- [ ] 完成或关闭后，相关列表、详情和按钮刷新，不能继续提交无效操作。
- [ ] 加载和发送时不反复点出重复请求；网络结果未知时先查询，不自动重发。
- [ ] 返回页面、选图返回、重新进入和普通进程重启后，不使用已关闭的网络对象或显示旧主机结果。
- [ ] 三台真机全程使用正式界面，走通发布、查找、申请和归还。
- [ ] 主机停止时客户端提示失败，恢复后能继续查询；主机普通重启后原数据仍在。

这些是对前端新增界面和对接行为的验收，A、B 已通过的底层测试不要求为了做界面从头重写或重复全部运行。改动公共基础代码时，再针对受影响部分补测。

## 十 你的第一天任务

第一天先不做复杂首页设计、底部导航和所有图片效果。这个小闭环做通后，再按第八节逐步补齐本计划。
